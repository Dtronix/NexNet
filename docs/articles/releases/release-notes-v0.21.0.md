# NexNet v0.21.0

*Unreleased*

## Security/correctness

- **Fixed: data from one connection could appear in another connection (HttpSocket and WebSocket).** When an HttpSocket or WebSocket connection closed while a read was still in progress, the transport returned the read's buffer to the shared buffer pool before the read finished. Another connection in the same process (another client's session on a server) could then get that buffer, and the late bytes of the closed connection landed in its incoming data. The other session could receive foreign protocol headers, invocations or pipe data (usually ending with `ProtocolError`), and data could be disclosed across sessions. Affected 0.20.0 and earlier, on both clients and servers (`NexNet.Asp`). Now only the read loop completes a transport's input, after its read has ended: `HttpSocketDuplexPipe.CompleteAsync` no longer completes `Input` (its reader completes it), and `IWebSocketPipe.CompleteAsync` stops the receive loop and waits for it to exit (up to 250 ms) before the input is completed; it no longer completes the input's reader. Upgrading is recommended for every HttpSocket and WebSocket user.

## Behaviour changes

- **Behavior change: the client derives its ping interval from the server's idle timeout.** `ServerGreeting` carries a new trailing field, `idleTimeoutMs`: the `Timeout` of the endpoint that accepted the session. `ClientConfig.PingInterval` is now `int?` and null by default. When it is null, the client pings at a third of the advertised timeout, at least every second, so a server with a short `Timeout` no longer times out clients that use the default interval. Against a server that advertises no timeout, the client pings every 10 s, as before. An explicit `PingInterval` is used as is; if it is not below the server's `Timeout`, the client logs a warning on connect. Client snapshots carry the interval in use as `NexusSessionSnapshot.PingInterval`. Setting `PingInterval` to zero or a negative value now throws `ArgumentOutOfRangeException`. Code that reads `PingInterval` as an `int` must handle null. See [Sessions & Lifetimes: Ping and Keep-Alive](../sessions-and-lifetimes.md#ping-and-keep-alive) and the [protocol specification](../../internals/protocol-specification.md) §4.2 and §5.5.
- **Behavior change: `MapWebSocketNexus` / `MapHttpSocketNexus` with a configuration that is not the server's primary one now apply that configuration's session settings.** Before, such a mapping only contributed its path and ASP.NET options, and its sessions used the primary configuration's `Timeout`, `MaxMessageSize`, flow control and `Authenticate`. When the server is already configured at mapping time, the configuration now becomes its own endpoint (see [Multiple Endpoints](../asp-net-integration.md#multiple-endpoints)). Mapping the primary configuration behaves exactly as before.

- **Behavior change: a call canceled before it is sent throws `TaskCanceledException`.** When the `CancellationToken` of a `ValueTask` or `ValueTask<T>` method is already canceled, or is canceled while the call waits for invocation credit, the call now throws `TaskCanceledException`. Before, `ValueTask` completed successfully and `ValueTask<T>` returned `default`, so a canceled call could not be told apart from a real result. As before, nothing is sent and no invocation ID is used. Fire-and-forget (`void`) methods and broadcasts are unchanged. See [Hub Invocations: Cancellation](../hub-invocations.md#cancellation).
- **Behavior change: the client gets its authentication token before the transport connects.** `ClientConfig.Authenticate` is now called before the connection opens rather than after. If it throws, no connection is opened: `TryConnectAsync` returns a failed `ConnectionResult` (`StateValue.Exception`, `DisconnectReason.Authentication`) carrying the exception, and `ConnectAsync` rethrows it. Before, the exception escaped `TryConnectAsync` and left the transport open. See [Authentication](../authentication.md#asynchronous-token).
- **Plaintext transports log a warning.** A client on plain TCP, `ws://` or `http://` logs `NexNet: unencrypted transport (<transport>); credentials and data are visible on the network.` at Warning level, once per client instance on its first connect. UDS, TLS, QUIC, `wss://` and `https://` do not warn. A custom `ClientConfig` subclass warns, named by its type, unless it overrides `IsSecureTransport` to return true. See [Authentication: Plaintext Transports](../authentication.md#plaintext-transports).
- **Behavior change: a collection's `ReadyTask` fails when the collection disconnects before its first synchronization.** Each `EnableAsync()` now starts a fresh `ReadyTask`, which fails with `InvalidOperationException` when the enable fails or the collection disconnects before its initial synchronization completes. `INexusList.ConnectAsync()` therefore throws in that case. Before, `ReadyTask` never completed and `ConnectAsync()` waited forever (or returned quietly for a collection that was never synchronized). See [Synchronized Collections](../synchronized-collections.md#connection-lifecycle).
- **Behavior change: a collection whose message processor fails is restarted or disabled.** On the server, a collection message processor that stops on an unexpected error is restarted after a backoff (100 ms, doubling), and the collection pipes of its clients are closed so they resynchronize. After 5 restarts within one minute, the next failure stops the collection: its clients are disconnected from it and new enables are refused until the server restarts. On a client, a processor failure disables the collection: `State` becomes `Disconnected`, `ReadyTask` fails and a pending `EnableAsync()` throws. Plain client lists must call `EnableAsync()` or `ConnectAsync()` again; relay collections re-enable themselves. Before, the collection silently stopped processing changes. See [Synchronized Collections: Failures](../synchronized-collections.md#failures).
- **`INexusList.State` reports the collection's real state.** It is `Connected` once the initial synchronization completes and `Disconnected` before it and after the collection pipe closes. Before, it did not track the collection.
- **An unauthorized pipe, channel or collection connect refuses the caller's pipe.** When `OnAuthorize` returns `AuthorizeResult.Unauthorized` for a method with an `INexusDuplexPipe` or `INexusDuplexChannel<T>` parameter, or for a synchronized collection connect, the server now sends `Refused` for the caller's pipe, as it does when the pipe limit is reached. The caller's `ReadyTask` (for a channel, `BasePipe.ReadyTask`; for a collection, `EnableAsync()`) fails at once with `NexusBusyException` and the session stays up. Before, nothing was sent and `ReadyTask` waited until the session ended. The wire protocol is unchanged, so the client cannot tell an authorization refusal from a limit refusal. `AuthorizeResult.Disconnect` still disconnects the session. See [Authorization](../authorization.md#authorization-results).

## New features

- **Java and JavaScript clients.** A server nexus opts in with `Targets = NexusTargets.Java | NexusTargets.JavaScript` (or `[assembly: NexusClientExport<TServer, TClient>]`), and the build writes a Java client (Java 11+, Android API 24+; WebSocket, HttpSocket, TCP and TLS) and a JavaScript client (Node 22+ with WebSocket, HttpSocket, TCP, TLS and UDS; browsers with WebSocket) into the directories set by `NexNetJavaOutputDir`/`NexNetJavaPackage` and `NexNetJavaScriptOutputDir`. The clients have the C# client's features: invocations and cancellation, client nexus methods, pipes, channels, synchronized collections, greeting-token authentication, reconnection, the client pool, logging, metrics and snapshots. The generator also writes each client's runtime next to the generated code (`EmitRuntime`, on by default; `RuntimeImport` for JavaScript, `Nullness` for Java), so nothing is installed from npm or Maven: the clients are distributed only through `NexNet.Generator`. See [Multi-language Clients](../multi-language-clients.md), [JavaScript Client](../javascript-client.md) and [Java Client](../java-client.md).


- **`ClientConfig.AuthenticateAsync`.** An asynchronous authentication token provider, `Func<CancellationToken, ValueTask<Memory<byte>>>`, for tokens fetched or refreshed from an identity provider. It is called on every connect and reconnect, before the transport connects, and must complete within `HandshakeTimeout`. Setting both `Authenticate` and `AuthenticateAsync` is a configuration error. See [Authentication](../authentication.md#asynchronous-token).
- **`INexusClient.IsSecure`.** True when the client's transport is encrypted or local (TLS, `wss://`, `https://`, QUIC, UDS); false for plain TCP, `ws://` and `http://`. Client snapshots carry it as `NexusSessionSnapshot.IsSecure` (null on server sessions). `ClientConfig.IsSecureTransport` defaults to false, so a custom `ClientConfig` subclass reports `IsSecure` false unless it overrides it.
- **WebSocket `AllowedOrigins`.** `WebSocketServerConfig.AllowedOrigins` restricts the `Origin` header of WebSocket requests to prevent Cross-Site WebSocket Hijacking when cookies are used. A request from another origin is answered 403. Empty (the default) allows every origin, as before. `UseWebSocketNexusServerAsync` passes the list to `WebSocketOptions.AllowedOrigins`, and `MapWebSocketNexus` checks it on every request. See [ASP.NET Integration: Browser Clients](../asp-net-integration.md#browser-clients).
- **Opt-in query-string access token.** `AccessTokenQueryParameter` on `WebSocketServerConfig` and `HttpSocketServerConfig` (null by default) promotes a query-string token to `Authorization: Bearer <token>` before `AspAuthenticationScheme` runs, for clients such as browsers that cannot send the header. The parameter is removed from the request's query string and its value is never logged by NexNet. The NexNet greeting token remains the canonical mechanism. See [ASP.NET Integration: Browser Clients](../asp-net-integration.md#browser-clients).
- **One server, many endpoints.** `NexusServer.AddListener(config, name)` adds TCP, TLS, UDS or QUIC listeners and `AddExternalEndpoint(config, name)` adds externally fed endpoints, next to the endpoint built from the primary configuration; `server.Endpoints` lists them. Each endpoint's configuration supplies its sessions' settings (timeouts, message size, flow control, `Authenticate`, TLS and ASP.NET options); logger, time, meter factory, rate limiting (counted across all endpoints) and `MaxPendingHandshakes` stay server-wide. Start binds every listener and rolls all of them back if one fails. When the primary configuration sets `Authenticate`, `StartAsync` throws unless every endpoint does. See [Transports: Multiple Endpoints](../transports.md#multiple-endpoints).
- **`Context.Endpoint`** (`NexusEndpointInfo(Name, Transport, IsSecure, Path)`) tells a server nexus which endpoint accepted the session, from `OnAuthenticate` onward. For WebSocket and HttpSocket, `IsSecure` is `HttpRequest.IsHttps`.
- **`NexusEndpointInfo.BoundEndPoint`**: the end point a TCP, TLS, UDS or QUIC listener actually bound, set while the server runs, so listeners can bind port 0 and report the picked port (also in `GetSnapshot().Endpoints[i].Address`). `Context.Endpoint` carries it too.
- **Per-endpoint metrics and snapshots.** Server instruments carry a `nexnet.endpoint` tag with the endpoint name (the primary endpoint is named after its transport, for example `tcp`). `NexusServerSnapshot.Endpoints` gives each endpoint's state, address and session count, and `NexusSessionSnapshot.Endpoint` the endpoint of a server session. Sessions of an added endpoint log under `SV{id}/{name}`.
- **NexNet.Asp: endpoints and hosted lifecycle.** `MapNexusWebSocket(server, config)` and `MapNexusHttpSocket(server, config)` map a WebSocket or HttpSocket endpoint of a configured server. `AddNexusServer(o => { o.Configure(primary); o.AddListener(tcp, "tcp"); })` configures the server and registers a hosted service that starts it once the application has started (after Kestrel binds) and stops it when the application stops. `UseWebSocketNexusServerAsync` and `UseHttpSocketNexusServerAsync` attach to an already configured server instead of throwing. See [ASP.NET Integration: Multiple Endpoints](../asp-net-integration.md#multiple-endpoints).
- **`[NexusJsNumber]`: checked `number` for `long`/`ulong` in generated JavaScript.** The generated JavaScript client maps C# `long` and `ulong` to `bigint` by default. `[NexusJsNumber]` on a `[NexusObject]` member, a nexus method parameter or return value (`[return: NexusJsNumber]`), a channel parameter or a collection property, or `[assembly: NexusJsNumber]` for the whole assembly, maps those values to a safe-integer `number` instead (including inside nullables, sequences, dictionaries, tuples and generic type arguments; primitive arrays such as `long[]` stay `BigInt64Array`). Writing or reading a value beyond ±(2^53 − 1) fails. The wire format, the C# and Java APIs and the nexus hashes are unchanged.
- **`NexusServerState.Starting` and `NexusServerState.Stopping`.** `State` now reports `Starting` while `StartAsync` binds its listeners and `Stopping` while `StopAsync` disconnects sessions; no session is accepted in either. Code that only compares against `Running` and `Stopped` is unaffected; code that switches over every value should handle the two new ones.

## Fixes

- **Fixed: a call could wait forever after the session disconnected.** A `ValueTask` or `ValueTask<T>` call made while its session was closing (for example while the server disconnected it) could register just after the disconnect had canceled every pending call. It was then sent and, with no result ever coming, never completed (about 1 in 3000 server-initiated disconnects under load). Such a call now throws `TaskCanceledException` at once, as calls pending at the disconnect do, and nothing is sent.
- **`DisconnectedTask` is completed after a failed connect attempt.** When `ConnectAsync`, `TryConnectAsync` or a reconnection attempt failed to open the transport (no server listening, a TLS failure, a canceled connect), `NexusClient.DisconnectedTask` was replaced by a task that never completed, so code awaiting it (and `IRentedNexusClient.DisconnectedTask` after a failed `EnsureConnectedAsync`) waited forever. `DisconnectedTask` now changes only once the transport is connected; after a failed attempt it stays completed.
- **NexNet.Quic no longer requires preview features.** The package was marked `[RequiresPreviewFeatures]`, a holdover from when `System.Net.Quic` was a preview API (it has been stable since .NET 9). Projects using NexNet.Quic no longer need `EnablePreviewFeatures`. Before, a `net10.0` project built with a newer SDK (such as SDK 11) failed with CA2252 even with `EnablePreviewFeatures` set, because the SDK only marks a project as preview when it targets the newest framework.

- **Duplicate nexus method names are reported as NEXNET042 instead of crashing the generator.** A nexus interface that overloads a method name, or declares a name that an inherited interface also declares, made the source generator throw, so the build reported only a generator failure (CS8785). It is now the error NEXNET042, reported at the duplicate method, and that nexus is not generated. Method names must be unique across a nexus interface and its inherited interfaces. A nexus class that overloads the name of an authorized method no longer crashes the generator either; the authorization of the overload that implements the interface method is used.
- **TLS and QUIC handshakes no longer block the accept loop.** A TLS connection now takes its `MaxPendingHandshakes` slot and its rate-limit slot when it is accepted, before the TLS handshake, and the handshake runs on its own task, bounded by `HandshakeTimeout` and the server's stop; a failed handshake frees both slots. A QUIC connection that never opens a stream is dropped after `HandshakeTimeout` instead of blocking the listener. The server and client set the NexNet ALPN on a copy of the SSL options, leaving the caller's (possibly shared) options unchanged.
- **Listener accept errors.** An accept error on a TCP, UDS or TLS listener no longer surfaces as a `NullReferenceException`: fatal errors are rethrown and transient ones skipped. A client that fails its QUIC handshake no longer stops a QUIC server.
- **QUIC endpoints.** Adding a QUIC endpoint whose UDP end point overlaps another endpoint's is rejected when it is added, like overlapping TCP ports. Server snapshots report a QUIC endpoint's address.
- **Server restarts.** Restarting a server with collections right after stopping it no longer fails with "Broadcaster is already running". In fast stop/start cycles, a late accept failure of the previous run no longer faults or stops the restarted server, and its accept loop no longer keeps spinning. A collection pipe flush canceled after the server stopped no longer raises an unobserved `ObjectDisposedException`.
- **Synchronized collection fixes.**
  - A new client receives its snapshot before any change; before, a change made while it connected could arrive ahead of the snapshot.
  - A request that loses a race to a concurrent change is answered with `Noop` after the winning change is broadcast, and the `Noop` completes the client's pending operation (it returns `false`). Before, the operation could wait forever.
  - A request based on a version older than the server keeps is answered with `Noop` instead of closing the collection pipe, and requests are rebased correctly across a `Clear`.
  - A malformed synchronization from the server (a protocol error) closes the collection pipe instead of leaving the list inconsistent.
  - A refused `EnableAsync()` (pipe limit or authorization), and a collection whose connection ends, return their pipe; refused enables no longer leak pipe slots.
  - Clients connected to a relay collection now follow the relay when it resynchronizes from its parent. When the relay reconnected to its parent, or the parent's list was cleared or had an item moved, the relay updated its own list but sent nothing to its clients, which kept stale data until they enabled the collection again. The relay now sends its connected clients a reset with its new list, as it does for a new client, and later changes apply on top of it. See the [protocol specification](../../internals/protocol-specification.md) §12.2.
  - Large snapshots arrive whole. The server wrote a new client's snapshot into the client's 1000-message outgoing buffer without waiting and dropped what did not fit, so a list of roughly 40,000 items or more could reach a client incomplete; the client then closed the collection as a protocol error (value count mismatch) and the enable failed. The snapshot is now written through the pipe's flow control, so a list of any size reaches even a slow client whole, for both `NexusList` collections and relay collections. A client that falls more than 1000 messages behind on live changes is still disconnected from the collection, now with a logged reason; enabling it again resynchronizes it. See the [protocol specification](../../internals/protocol-specification.md) §12.5 and §12.8.
- **A pipe closing while a write is in flight no longer drops the session.** When a pipe, channel or collection pipe was closed or reset while the application was still writing or flushing to it, the flush could send from buffers already returned to the pool, or send data after the pipe's completion; the session then ended with a protocol error, taking every other pipe and pending call with it (for example, a client that disabled a collection mid-stream had its next `EnableAsync()` fail with `TaskCanceledException`). Now only that pipe ends: data written after the close is dropped, buffers are released only once no flush or caller still uses them, and nothing is sent for the pipe after its completion.
- **`DisconnectedTask` is completed after a failed connect attempt.** When `ConnectAsync`, `TryConnectAsync` or a reconnection attempt failed to open the transport (no server listening, a TLS failure, a canceled connect), `NexusClient.DisconnectedTask` was replaced by a task that never completed, so code awaiting it (and `IRentedNexusClient.DisconnectedTask` after a failed `EnsureConnectedAsync`) waited forever. `DisconnectedTask` now changes only once the transport is connected; after a failed attempt it stays completed.
- **Returning a pooled client after its `NexusClientPool` is disposed no longer throws.** Disposing an `IRentedNexusClient` after `NexusClientPool.DisposeAsync` disposed its client and then threw `ObjectDisposedException` from the pool's disposed semaphore. It now just disposes the client.
- **Generator diagnostics are reported at their source location.** Nexus validation and serialization diagnostics (NEXNET001 – NEXNET042) had no location, so the build and the IDE showed them without a file or line. They now point at the method, member, interface or class they are about.
