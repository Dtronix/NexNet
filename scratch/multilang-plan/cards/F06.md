# F06 — NexNet.Asp: WebSocket AllowedOrigins + opt-in query-string token

| Size | Lands on | Requires | Decision | Branch |
|---|---|---|---|---|
| S | **master** | — | D15 | `mt/F06-asp-origins-querytoken` |

## Problem (verified)
- **No Origin restriction.** `src/NexNet.Asp/NexNetMiddlewareExtensions.WebSocket.cs:134` calls `app.UseWebSockets()` with default options. With cookie auth, that allows cross-site WebSocket hijacking.
- **No browser auth header.** Browsers cannot send an `Authorization` header on a WebSocket.

## Owns
- `src/NexNet.Asp/**`
- the WebSocket and HttpSocket server config types, if the new options belong there
- tests: `AspClientServerTests.cs` and a new `AspWebSocketOriginTests.cs`
- `docs/articles/asp-net-integration.md`
- `docs/articles/authentication.md`
- release notes

## Steps
1. **`AllowedOrigins` for WebSocket.**
   - Add `AllowedOrigins` (`IList<string>`; empty means allow all, which preserves today's behavior).
   - Apply it through `WebSocketOptions.AllowedOrigins`.
   - Also check it per request in `MapWebSocketNexus`, returning 403 on a mismatch.
   - Mirror the semantics of the existing `HttpSocketOptions.AllowedOrigins`.
2. **Opt-in query-string token.** Add `AccessTokenQueryParameter` (for example `"access_token"`; null means disabled) to the WebSocket and HttpSocket server configs.
   - When it is set and the request has no `Authorization` header, promote the query value to `Authorization: Bearer <token>` before `ApplyAuthentication` runs.
   - Redact the query value in NexNet logs.
3. **Docs.** Document browser auth:
   - the greeting token is the canonical mechanism;
   - the query token is only for ASP.NET auth that runs before the upgrade;
   - set `AllowedOrigins` whenever cookies are used.
4. **Tests:**
   - an allowed origin connects and a blocked origin gets 403;
   - a query-string token authenticates;
   - the query token is disabled by default.
