# S03 — TLS/QUIC handshakes off the accept loop

| Size | Lands on | Requires | Branch |
|---|---|---|---|
| S | train | S02 | `mt/S03-handshake-off-loop` |

## Problems
- **TLS head-of-line blocking.** `TcpTlsTransport.CreateFromSocket` (`src/NexNet/Transports/Tcp/Tls/TcpTlsTransport.cs`, ~L60-74) runs the TLS handshake inside the accept loop. One slow client blocks every other TLS accept for up to `SslConnectionTimeout` (5 s).
- **QUIC can block forever.** `QuicTransport` calls `AcceptInboundStreamAsync(CancellationToken.None)` inside the accept loop. A peer that never opens a stream blocks that listener permanently.
- **Shared ALPN mutation.** `QuicTransportListener.Create` mutates the shared `SslServerAuthenticationOptions.ApplicationProtocols`, which leaks `nn1` into TLS listeners that share the same options.

## Owns
- `src/NexNet/Transports/Tcp/Tls/*`
- `src/NexNet.Quic/**`
- `src/NexNet/NexusServer.cs` (**hot**; the accept path only)
- tests

## Steps
1. The accept loop only accepts the raw socket or connection. Each TLS handshake and QUIC stream accept runs on its own task:
   - bounded by its handshake timeout;
   - counted against `MaxPendingHandshakes`;
   - preceded by the rate-limiter check.
2. Copy the SSL options before setting the QUIC ALPN.
3. Tests:
   - 10 stalled TLS clients do not delay an 11th, which connects in under 1 s;
   - a QUIC peer that opens no stream does not block others;
   - the ALPN of a shared options object stays unchanged.

## Verify
The full C# gate. QUIC tests run only where msquic is available, as they do today.
