# F08 — Regenerate test certificates (CA + SAN leaf)

| Size | Lands on | Requires | Unblocks | Branch |
|---|---|---|---|---|
| S | train | — | H04 | `mt/F08-test-certs` |

## Problem (verified)
`src/server.pfx` has the subject `CN=127.0.0.1, CN=localhost`, **no extensions and no SAN**, and expires 2033-04-29. Java, Node and Chromium all reject it.

## Owns
- `src/NexNet.IntegrationTests/certs/` (new):
  - `test-ca.pem`
  - `test-ca.key` (test-only, documented as such)
  - `server.pfx`, `server.pem`, `server.key`
  - `client.pfx`, `client.pem`, `client.key`
  - `README.md`
- `tools/certs/generate-test-certs.ps1` (reproducible, uses .NET `CertificateRequest`)
- `src/NexNet.IntegrationTests/NexNet.IntegrationTests.csproj` (copy items)
- `src/NexNet.IntegrationTests/BaseTests.cs` (**hot**; certificate path only)
- `src/NexNet.IntegrationTests/TlsCertificateTests.cs`
- every other `server.pfx` user (`src/Samples/**`, `src/NexNetBenchmarks/**`): update each one, or keep the old file for them

## Steps
1. Write the generator script. It produces:
   - a test CA valid for 10 years;
   - a server leaf with SAN `DNS:localhost, IP:127.0.0.1, IP:::1` and EKU serverAuth, valid for 5 years;
   - a client leaf with EKU clientAuth.

   PFX files keep the password `certPass`.
2. Point the tests at the new files.
   - Tests that intend validation must trust the test CA explicitly, not accept everything.
   - Tests that intend to see an untrusted server must still see one.
3. Write the server leaf's SPKI sha256 pin, base64, into `README.md`. Later Node, Java and browser pin tests use it.
4. Grep for every use of `server.pfx` and update each one.

## Acceptance
- All TLS tests pass.
- `openssl x509 -in server.pem -noout -ext subjectAltName`, or the .NET equivalent, lists the SANs.
